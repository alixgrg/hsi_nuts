# Notebook 05 - SIMCA Validation Robustness Review

## Role In The Workflow

`notebooks/05_simca_validation_robustness.ipynb` reviews the validation-stage SIMCA candidates generated by notebook 04C.

It is a diagnostic notebook, not a final-selection notebook:

- it uses only validation outputs from batch 3;
- it does not load or evaluate the pure-test split;
- it does not choose final models;
- it produces scoring, flags, Pareto fronts, ablation summaries, optional random-state stability checks, optional border/core diagnostics, and optional duplicate-candidate diagnostics.

The next workflow stages should use this notebook as a robustness screen before pure-test evaluation and final multi-model selection.

## How To Use The Notebook

For a quick validation review, keep:

```python
RUN_RANDOM_STATE_STABILITY = False
RUN_BORDER_CORE_DIAGNOSTICS = True
RUN_DUPLICATED_CANDIDATE_ANALYSIS = True
```

This computes all non-refit diagnostics and records a skipped border/core status if pixel tables are absent.

To run random-state stability:

```python
RUN_RANDOM_STATE_STABILITY = True
STABILITY_RANDOM_STATES = tuple(expcfg.SIMCA_ROBUSTNESS_RANDOM_STATES)
MAX_STABILITY_CANDIDATES_PER_TRACK = expcfg.SIMCA_ROBUSTNESS_MAX_STABILITY_CANDIDATES_PER_TRACK
```

This refits a compact panel of candidates over several seeds. The panel is intentionally limited because each seed triggers model refits. The diagnostic is especially relevant for `balanced_pixels` models.

To run border/core diagnostics:

1. Rerun notebook 04C with `SAVE_BATCH_PIXEL_TABLES=True`.
2. Run notebook 05 with `RUN_BORDER_CORE_DIAGNOSTICS=True`.

The resulting table compares object-level metrics when border pixels are excluded from the object decision.

## Scientific Logic

### Random-State Stability

Random-state stability checks whether metrics vary when stochastic parts of the workflow change. The main stochastic risk is the `balanced_pixels` matrix family, where pixels are sampled per object.

The notebook first builds `random_state_stability_panel.parquet`, then optionally runs refits through `run_selected_simca_random_state_stability(...)`.

### Border/Core Diagnostics

Border/core diagnostics evaluate whether object decisions rely strongly on border pixels. This is important because borders are more likely to include mixed pixels, segmentation uncertainty, or partial object/background contamination.

The diagnostic uses detailed pixel prediction tables from 04C. If those tables are not present, the notebook does not guess: it writes a skipped status table.

### Hyperparameter Ablation

Ablation summaries are observational. They compare performance distributions across values of one hyperparameter at a time:

- matrix method;
- training matrix id;
- preprocessing;
- SIMCA rule;
- number of components;
- object threshold;
- Savitzky-Golay parameters;
- position dilation radius;
- balanced-pixel strategy.

This is not a refit-based ablation experiment. It is a screening table for model-selection discussions.

### Pareto Fronts

The 2-way Pareto front minimizes:

- `fn_rate`;
- `fp_rate`;

and maximizes:

- `balanced_accuracy`.

The 3-way Pareto front minimizes:

- `target_miss_rate`;
- `non_target_false_accept_rate`;
- `uncertain_rate`;

and maximizes:

- `coverage_rate`;
- `screening_sensitivity`;
- `decided_balanced_accuracy`.

Pareto status is computed independently by track and matrix family.

### Duplicate-Candidate Diagnostics

Notebook 04C can remove candidates that have identical metrics while only one logical parameter group differs. Notebook 05 summarizes those groups and, when available, reads the optional duplicated-refit comparison table produced by 04C.

The duplicate review status is:

- `verified_equal`: post-refit metrics are still identical and match pre-refit metrics;
- `equal_after_refit_changed_from_pre`: post-refit metrics remain equal but changed from pre-refit values;
- `diverged_after_refit`: post-refit metrics are not identical;
- `not_refit`: a group exists but was not part of the optional duplicated refit output;
- `not_run`: no duplicated-refit comparison table was available.

## Interpretation Notes

High robustness scores and Pareto-front membership are useful evidence, but they are not final decisions. A candidate can be good on validation and still fail pure-test evaluation.

Recommended interpretation order:

1. Check `track_scoring_flags.parquet` by selection track.
2. Inspect Pareto fronts for 2-way and 3-way trade-offs.
3. Review high-impact ablation factors.
4. Run random-state stability for the strongest `balanced_pixels` candidates.
5. Run border/core diagnostics if pixel tables were saved.
6. Use the resulting evidence to decide which candidates should go to pure-test evaluation.
